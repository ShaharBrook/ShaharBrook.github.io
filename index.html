The problem

הבעיה

A studio running campaigns for many clients holds the most sensitive thing each of those clients owns — their footage, their spend, their numbers. It also has to let those clients log in to review work, and that is the hard part: every external login is another route by which one client's data could reach another.

סטודיו שמנהל קמפיינים לכמה לקוחות מחזיק בדבר הרגיש ביותר שיש לכל אחד מהם — החומרים, התקציב והמספרים שלו. הוא גם צריך לתת לאותם לקוחות להיכנס ולאשר עבודות, וזה החלק הקשה: כל התחברות חיצונית היא עוד דרך שבה נתונים של לקוח אחד עלולים להגיע לאחר.

What I built

מה בניתי

Clients, campaigns, tasks across kanban/list/calendar views, a file repository with video streaming, threaded review comments, a finance ledger and an in-app AI assistant — in a bilingual Hebrew/RTL interface. A TypeScript monorepo: NestJS 11 and PostgreSQL/Prisma behind React 19, shipped as a single Docker image. Roughly 46k lines, 31 data models, 108 API operations.

לקוחות, קמפיינים, משימות בתצוגות קנבן/רשימה/לוח שנה, מאגר קבצים עם סטרימינג וידאו, שרשורי הערות, ספר חשבונות פיננסי ועוזר AI מוטמע — בממשק דו־לשוני בעברית ובכתיב מימין לשמאל. מונורפו ב־TypeScript: NestJS 11 ו־PostgreSQL/Prisma מאחורי React 19, נשלח כאימג' Docker אחד. כ־46 אלף שורות, 31 מודלי נתונים, 108 פעולות API.

Key decisions

ההחלטות המרכזיות

  • Authorization rules double as database query filters. A permission rule's conditions are Prisma where fragments, so the rule that answers "may this user edit this record?" is the filter on the list query. A list endpoint and a per-record check cannot disagree, because they are the same rule. External clients are default-deny and permitted positively — the finance ledger has no rule under any flag, so it is structurally unreachable rather than merely hidden.
  • כללי ההרשאות משמשים גם כמסנני שאילתות במסד הנתונים. התנאים של כלל הרשאה הם קטעי where של Prisma, כך שהכלל שעונה על "האם המשתמש הזה יכול לערוך את הרשומה?" הוא המסנן של שאילתת הרשימה. בדיקה נקודתית ורשימה לא יכולות לסתור זו את זו, כי הן אותו כלל. לקוחות חיצוניים חסומים כברירת מחדל ומקבלים היתרים מפורשים בלבד — לספר החשבונות אין כלל באף דגל, ולכן הוא בלתי נגיש מבנית ולא רק מוסתר.
  • No passwords, and no token an XSS payload can read. Google sign-in only; access tokens live in memory, never in localStorage. The refresh token is deliberately not a JWT — 256 bits of opaque entropy stored only as a SHA-256 digest, so a database dump hands out no live sessions. It rotates on every use, and presenting an already-rotated token revokes the entire token family.
  • בלי סיסמאות, ובלי טוקן שקוד XSS יכול לקרוא. התחברות דרך Google בלבד; טוקני הגישה נשמרים בזיכרון, לא ב־localStorage. טוקן הרענון הוא בכוונה לא JWT — 256 ביט של אנטרופיה אטומה שנשמרת רק כתקציר SHA-256, כך שהדלפת מסד נתונים לא מחלקת סשנים חיים. הוא מתחלף בכל שימוש, והצגה של טוקן שכבר הוחלף מבטלת את כל משפחת הטוקנים.
  • One contract, from the database to the browser. Shared Zod schemas derive the API's DTOs, which produce the OpenAPI document, which generates the browser's typed client. Change a field once and the compiler finds every consumer — there is no hand-written type on either side of the wire to drift. Soft delete works the same way: a Prisma client extension rewrites deletes and folds the filter into every read, so a service that forgets a where clause cannot resurrect deleted rows.
  • חוזה אחד, ממסד הנתונים ועד לדפדפן. סכמות Zod משותפות מגדירות את ה־DTOs של ה־API, שמייצרים את מסמך ה־OpenAPI, שממנו נוצר קליינט מוטיפס לדפדפן. משנים שדה פעם אחת והקומפיילר מוצא כל צרכן — אין טיפוס שנכתב ביד באף צד של החוט שיכול לסטות. מחיקה רכה עובדת באותו אופן: הרחבת קליינט של Prisma משנה מחיקות ומשלבת את הסינון בכל קריאה, כך ששירות ששוכח where לא יכול להחיות שורות מחוקות.
  • Multi-gigabyte video uploads — and the bug underneath them. Large files go through resumable chunked sessions: chunks written to shared storage so a load balancer cannot split a transfer, per-chunk length verification because a truncated chunk recorded as complete yields a file of the right size that is quietly corrupt, and idempotent completion. The real cause of "large uploads fail sometimes" was Node's server.requestTimeout — a five-minute default that silently caps how long any upload may take however healthy the transfer is, and reaches the browser as a connection error with no status.
  • העלאות וידאו בגודל ג'יגה־בייטים — והבאג שמתחת להן. קבצים גדולים עוברים בסשנים מקוטעים שניתן להמשיך: הקטעים נכתבים לאחסון משותף כדי שמאזן עומסים לא יפצל העברה, אורך כל קטע מאומת כי קטע קטוע שנרשם כהושלם מייצר קובץ בגודל הנכון שפשוט פגום, וההשלמה אידמפוטנטית. הסיבה האמיתית ל"העלאות גדולות נכשלות לפעמים" הייתה server.requestTimeout של Node — ברירת מחדל של חמש דקות שחוסמת בשקט את משך ההעלאה, בלי קשר לבריאות ההעברה, ומגיעה לדפדפן כשגיאת חיבור בלי סטטוס.

Result

התוצאה

In production, in daily use by the studio team — including from a phone on set. 647 automated tests across five suites, including API end-to-end against a real PostgreSQL instance with Prisma never mocked, and a dedicated Hebrew RTL browser suite.

בפרודקשן, בשימוש יומי של צוות הסטודיו — כולל מהטלפון בזמן צילומים. 647 בדיקות אוטומטיות בחמש חבילות, כולל בדיקות API מקצה לקצה מול מופע PostgreSQL אמיתי בלי למוק את Prisma, וחבילת בדיקות דפדפן נפרדת ל־RTL בעברית.

The problem

הבעיה

A marketing agency's own site is the hardest brief there is, because the page is the product demo. If the site that sells lead generation does not generate leads, nothing written on it is believable. This one is ours, so there was nowhere to hide.

האתר של סוכנות שיווק הוא הבריף הקשה ביותר שיש, כי הדף עצמו הוא ההדגמה של המוצר. אם האתר שמוכר יצירת לידים לא מייצר לידים, שום דבר שכתוב בו לא אמין. הדף הזה הוא שלנו, אז לא היה איפה להתחבא.

What I built

מה בניתי

A Hebrew right-to-left landing page built around a single action — booking a free growth call, answered within 24 hours. I designed it, structured the content, built it and host it.

דף נחיתה בעברית ובכתיב מימין לשמאל, שבנוי סביב פעולה אחת — קביעת שיחת צמיחה בחינם, עם מענה תוך 24 שעות. עיצבתי, בניתי את מבנה התוכן, פיתחתי ומאחסן אותו.

Key decisions

ההחלטות המרכזיות

  • Opened with a claim, not a service list. The page leads on "we don't build websites, we build lead machines" and only then says what that involves. A business owner is buying an outcome; the capability list is what convinces them you can deliver it, not what makes them want it.
  • נפתח בהצהרה, לא ברשימת שירותים. הדף מוביל עם "אנחנו לא בונים אתרים, אנחנו בונים מכונות לידים", ורק אחר כך מסביר מה זה כולל. בעל עסק קונה תוצאה; רשימת היכולות היא מה שמשכנע אותו שאתה מסוגל לספק אותה, לא מה שגורם לו לרצות אותה.
  • One action, repeated — every route through the page ends at the same button. A page with three competing calls to action converts on none of them.
  • פעולה אחת, חוזרת — כל מסלול בדף מסתיים באותו כפתור. דף עם שלוש קריאות לפעולה שמתחרות ביניהן לא ממיר באף אחת מהן.
